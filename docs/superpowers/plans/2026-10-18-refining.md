# Refining Implementation Plan

> **For agentic workers:** Each task below is implemented by opencode (`opencode-go/deepseek-v4.1-flash`) in its own session and reviewed by a separate opencode session; Claude orchestrates, smoke-tests UI in the browser and commits. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an MVP of issue #36: alloy and fuel as refined `Resource` kinds; a station refinery queue that converts ore → alloy and ice → fuel over time, persists in the save and is shown in a HUD panel; tier-3 components and the big hulls cost alloy and warps cost fuel; the balance bot refines and the report is re-tuned.

**Architecture:** `Resource` widens to five kinds with `RawResource` for the world (rocks, pickups, belts); pure recipe data in `src/data/refining.ts`; plain-JSON state (`Run.refinery`) in `src/sim/types.ts`; all logic in a new pure `src/sim/refining.ts` called once per tick; two new handler-map commands; save v3 → v4 migration; a `RefineryPanel` HUD module; cost table changes; bot + balance-report support.

**Tech Stack:** TypeScript, Three.js, Vite, vitest, oxlint/oxfmt

**Spec:** `docs/superpowers/specs/2026-10-18-refining-design.md`

## Global Constraints

- **`src/core`, `src/data`, `src/sim` stay pure:** no DOM, no three.js, no `Math.random`, no `Date`.
- **`src/data` stays a leaf:** `data/refining.ts` may import `./resources` only.
- **Determinism:** refining uses no RNG at all. `run.rng`, rock generation and contract boards must not change.
- **Refining never touches `run.runValue`.** A refined unit's `RESOURCE_INFO.value` equals its recipe input value per unit.
- **Early game unchanged:** tier-1/tier-2 component prices and the Mining Drone price do not change.
- Match the surrounding style: short header comment per module, `/** */` on exported functions and non-obvious fields, no comment noise. Format: oxfmt (printWidth 120, single quotes, trailing commas).
- Every task ends with `npm run check` passing (format:check, lint, typecheck, tests).
- Do not touch `scratch.md`. No new dependencies. Do not commit.

## Lifecycle checklist (UI and save tasks)

Every UI or save task must hold up across: **warp** (new run, empty queue, new system number), **loading another slot** (different seed, possibly identical queue shape), **new game**, and **an old save** (v2 and v3 fixtures). Reviewers check each explicitly; the orchestrator smoke-tests UI tasks in the browser.

## Review Focus

1. **Missing `alloy`/`fuel` keys** in a bank or cargo → `NaN` → bank poisoned. Task 2 (migration) and typecheck on every `Wallet` literal.
2. **Inputs paid twice / refunds wrong** on merge or cancel. Task 3 asserts exact bank deltas.
3. **Time leakage in `updateRefinery`:** leftover time lost or double-spent at batch/job boundaries. Task 3 asserts one big `dt` equals many small ones.
4. **Value created by refining** (HD farming). Task 1 pins value equality; Task 3 asserts `runValue` unchanged.
5. **Stale HUD after warp/load** (structure key reuse, see #35 run log). Task 5.
6. **Opening drift** from the cost/bot change. Task 6/7 compare opening milestones with `docs/balance.md`.

## Task 3: Refinery queue logic and the tick

**Files:** Modify `src/sim/refining.ts` (add `refineBlock`, `queueRefine`, `maxBatches`, `cancelRefine`, `updateRefinery`, `describeRecipe`, `jobProgress`, `queuedOutput`), `src/sim/update.ts` (call `updateRefinery(state, dt)` after `updateContracts`; update the tick-order header comment); Test: extend `tests/refining.test.ts`.

**Build (spec §4):**
- `refineBlock(run: Run, recipe: RecipeId, count: number): { n: number } | { error: string }` — pure validation, no mutation: `n = Math.floor(count)`; `n < 1` → `'Nothing to refine.'`; `n = min(n, refineMaxBatch)`; if the last job has the same recipe, `n = min(n, refineMaxBatch − last.count)` and `n < 1` → `'That refinery job is full.'`; else if `queue.length >= refineQueueMax` → `'Refinery queue is full.'`; cost = each input × n; not affordable → `` `Not enough ${RESOURCE_INFO[r].name.toLowerCase()} to refine ${n} ${RESOURCE_INFO[recipe].name.toLowerCase()}.` `` naming the first short resource (in `RESOURCES` order); else `{ n }`.
- `queueRefine(run, recipe, count): { queued: number } | { error: string }` — `refineBlock`, then `pay` `input × n` and merge into the last job (`count += n; total += n`) or push `{ recipe, count: n, total: n, progress: 0 }`. Any rejection leaves state untouched.
- `maxBatches(run, recipe): number` — largest `n` that `refineBlock` would accept (affordable batches, capped by `refineMaxBatch` and the merge headroom; 0 when the queue is full or nothing is affordable). Used by the HUD's Max button.
- `cancelRefine(run, index): RefineJob | null` — out of range → null; else remove, refund `input × count` into `run.bank`, return the job.
- `updateRefinery(state, dt)` — `let budget = dt`; loop while `budget > 0` and a front job exists: `need = time − progress`; if `budget >= need` → `budget −= need`, `bank[recipe] += output`, `produced[recipe] += output`, `count−−`, `progress = 0`, and if `count === 0` shift and log `info` `` `Refinery: ${total * output}${icon} ${name.toLowerCase()} ready.` `` (resource name, e.g. `alloy`); else `progress += budget`, `budget = 0`.
- `describeRecipe(id)` → `` `${formatCost(input)} → ${output}${icon} · ${time}s` ``; `jobProgress(job)` → `progress / time` in [0,1]; `queuedOutput(run, recipe)` → sum of `count × output` over jobs of that recipe (used by the bot and UI).

**Tests:** `refineBlock` returns each error message and the clamped `n`; `maxBatches` with 23 ore → 5 alloy batches, with a full queue → 0, with merge headroom; queue pays exactly `n × input`; merge with last same-recipe job (one job, `count`/`total` summed, paid once per call); different recipe appends; queue full rejected and unaffordable rejected with bank and queue unchanged; count floored, `0`/negative rejected, clamped to `refineMaxBatch`; cancel refunds unfinished batches (finish 2 of 5, cancel → refund 3 × input) and an unknown id returns null (job ids added after review); `updateRefinery`: after `time − ε` nothing produced, after `time` one unit; leftover carries across batches (1 job of 3 fuel, dt 2.5 → 2 fuel, progress 0.5) and across jobs (fuel 1 batch then alloy, dt 2 → 1 fuel, alloy progress 1); one `dt = 30` equals 1800 ticks of `1/60` (bank and `produced` equal within 1e-9; batch counts exact); `run.rng.s` and `run.runValue` unchanged after refining; completion logs exactly one `info` line per finished job; integration via `tick()` with `SimIndex`: queue fuel, tick 2 s → fuel in bank.

**Done when:** `npm run check` passes and the determinism test still passes.

## Task 7: Tuning with a robustness margin

**Files:** Tuning only: `src/data/refining.ts`, `src/data/tuning.ts`, `src/data/components.ts`, `src/data/hulls.ts`, `scripts/bot.ts` (policy fixes only); tests only if a tuned value is pinned by one (update deliberately). `docs/balance.md` is regenerated by the orchestrator, not the implementer.

**Targets** (compare with the committed `docs/balance.md` from main and a 20-seed baseline the orchestrator provides):
- Opening milestones (first purchase, first T2, first drone, fleet full): medians within ±10 % of baseline.
- Time in system: each system's median within ±15 % of baseline, **and** the same holds on a second disjoint seed set (`--seed-start 2000 --seeds 10`). Aim inside ±10 % to leave margin.
- No walls in either seed set.
- HD per system within ±1 of baseline median.
- Recipe value equality (Task 1 test) still holds: if a recipe ratio changes, change the refined value with it.

**Build:** run both seed sets, adjust recipe times first (the refining-at-warp delay), then refined prices; document each iteration in the final message as a table (knobs → per-system medians for both sets).

**Done when:** `npm run check` passes and both seed sets meet the targets.
